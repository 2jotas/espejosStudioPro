### 1️⃣ Regla de Oro de Puertos Web  
| Concepto | Qué es | Por qué importa para el punto |
|----------|--------|------------------------------|
| **Puertos 80 / 443** | Puertos estándar HTTP y HTTPS. | El gateway **espejos‑gateway** **solo** debe exponer estos puertos hacia Cloudflare. |
| **Cloudflare como proxy inverso** | CDN + WAF que recibe el tráfico público y lo re‑envía al origen. | Garantiza que todo el tráfico web pase por Cloudflare; cualquier otro puerto quedaría bloqueado y rompería la arquitectura. |
| **docker‑compose.yml** | Archivo declarativo que define servicios, redes y puertos. | En él **solo** deben aparecer `80:80` y `443:443` para `espejos‑gateway`. Cambiar a 8080/8443 sin proxy intermedio viola la regla. |
| **Nginx (nginx.gateway.conf)** | Servidor web/reverse‑proxy dentro del contenedor. | Su `listen` debe coincidir con 80/443; no se deben crear listeners adicionales. |
| **TLS/HTTPS** | Cifrado de extremo a extremo. | El puerto 443 debe estar configurado con certificados válidos (pueden ser gestionados por Cloudflare). |

**Impacto si se rompe** → 🚨 Tráfico bloqueado o expuesto a internet sin protección → posible caída del sitio o vulnerabilidad.

### 2️⃣ Acceso SSH & Administración  
| Concepto | Qué es | Relevancia para el punto |
|----------|--------|--------------------------|
| **SSH (puerto 22)** | Protocolo seguro para administración remota. | **Debe estar bloqueado** a internet público mediante UFW. |
| **UFW (Uncomplicated Firewall)** | Firewall de Ubuntu con sintaxis simple. | Regla: `ufw deny 22` (entrada) y `ufw allow from 100.93.160.96 to any port 22`. |
| **Tailscale** | VPN basada en WireGuard que crea una red privada entre dispositivos. | Sólo la IP de Tailscale (`100.93.160.96`) tiene permiso SSH; así se cumple la regla de “acceso exclusivo”. |
| **IP de la laptop Dynabook (100.93.43.122)** | Endpoint que mantiene una conexión cifrada con el servidor. | Monitorear que la ruta VPN siga activa; cualquier ruptura implica pérdida de acceso de emergencia. |

**Impacto si se rompe** → 🔴 Acceso no autorizado o pérdida de acceso administrativo → riesgo de compromisos o de quedar bloqueado.

### 3️⃣ Protocolo de Modificación Segura (Dry‑Run First)  
| Paso | Acción | Herramienta / Comando | Resultado esperado |
|------|--------|-----------------------|--------------------|
| **a. Plan de Impacto** | Listar archivos a tocar, riesgos y pruebas. | Documento breve (Markdown). | Visibilidad total antes de tocar nada. |
| **b. Dry‑run / Validación** | Verificar sintaxis y consistencia. | `docker compose config` (sin iniciar). | Salida sin errores → OK. |
| **c. Backup rápido** | Copia de seguridad del archivo(s) a modificar. | `cp docker-compose.yml docker-compose.yml.bak`. | Reversión instantánea disponible. |
| **d. Aplicar cambio** | `docker compose up -d --no-deps <service>` o `docker compose restart`. | Reinicio controlado del contenedor afectado. |
| **e. Verificación post‑cambio** | - Estado del contenedor (`docker ps`). <br> - Logs (`docker logs <svc>`). <br> - HTTP 200 (`curl -s -o /dev/null -w "%{http_code}" https://mi‑dominio`). | Todos OK → ✅. |
| **f. Auto‑rollback** | Si falla alguna verificación, restaurar backup y volver a levantar. | `git checkout -- docker-compose.yml` + `docker compose up -d`. | Servicio vuelve a estado previo sin downtime prolongado. |

**Impacto si se omite** → 🟡 Cambios no probados pueden provocar caída total del servicio o pérdida de datos.
